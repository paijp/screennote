# エージェント制御（MCP）— 選択肢と得失

claude.ai から、VPS を中継して Screennote の WebView を操作するための設計空間。
議論で挙がった選択肢を、採否を決めやすい形で並べたもの。**まだ何も実装されていない。**

前提となる構成:

```
[claude.ai] ──MCP(HTTPS)──> [VPS: nginx + PHP-FPM + SQLite]
                                    ↑
                               polling
                                    ↓
                      [Screennote: WebView]
```

UI の細部は後回しにして、まず端から端まで動くものを作る方針。最後の
「[最小構成](#最小構成)」がその選択。

---

## A. 新しいタブを開こうとしたとき

商品一覧から商品詳細へ、のような `target="_blank"` / `window.open` をどう扱うか。

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **A1. 何もしない（現状）** | 実装ゼロ | `window.open` が**黙って無反応**になる。Claude は成功と解釈して同じ操作を繰り返す。エージェント運用で最悪の壊れ方 |
| **A2. 同一ビューで開く**<br>（`window.open` を `location.href` に上書き） | 数行。タブ管理が不要 | opener 関係が失われ、**OAuth ポップアップが戻ってこない**（認証は成功するのに元ページに結果が返らない）。開いた窓に `document.write` するサイトが壊れる。注入タイミングが難しい（`addDocumentStartJavaScript` が要る） |
| **A3. 本物のタブを開く** | 実ブラウザと同じ挙動。特殊な振る舞いが無いぶん事故が減る。**タブ自体が成果物になる用途**（「商品ごとにタブを開いて」）に応えられる | 数百行。タブ横断の状態管理が増える。メモリ |

`window.open` を通すには `setSupportMultipleWindows(true)` と
`javaScriptCanOpenWindowsAutomatically = true`（既定は false）が要る。後者がポップアップ
ブロッカの正体で、Claude の `element.click()` が無反応になる直接の原因。

`onCreateWindow` には `isUserGesture` が渡るので、「JS 注入中に立てたフラグが on なら許可、
ページが勝手に呼んだものは `isUserGesture` で判断」というポリシーが書ける。**Claude の操作を
ユーザー操作とみなす**、という自然な形になる。

> サイトが `navigator.userActivation.isActive` を自分で見ている場合は上記では通らない。
> 注入スクリプトでの上書きが要るが、まず実測してから。

## B. タブの可視性

Claude にどのタブを見せるか。

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **B1. 1 枚だけ（タブなし）** | 最小。曖昧さがない | 上記 A3 の用途に応えられない |
| **B2. 全タブが見える** | 実装が単純 | ユーザーが作業中のタブの中身が読まれる。銀行・メールを開いたまま使えない |
| **B3. タブごとに「Claude 制御」チェックボックス** | 許可範囲が**タブ列として目に見える**。取り消しは「閉じる／チェックを外す」で、新しい UI が要らない。インジェクションの被害がチェック済みタブに閉じる | 規則を 3 つ決める必要がある（下記） |

B3 を成立させる規則:

1. **Claude が開いたタブは自動的に on。** そうでないと自分が作ったタブが見えない。
   「制御下のタブから生まれたタブは制御を継承する」。ユーザーが自分で開いたタブは既定 off
2. **実行中に外されたら明示的にエラーを返す。** 黙って何もしないのが最悪
3. **`window.opener` が境界を跨ぐ。** 制御下のタブ B の opener が制御外のタブ A を指し、
   同一オリジンなら、B に注入した JS から `A.document` に到達できる。**チェックボックスを
   JS が素通りする。** 境界を跨ぐ時点で `opener` を null 化すること

**重要**: B3 が制御するのは**可視性**であって**到達性**ではない。銀行のタブを隠しても、
Claude が自分で銀行のタブを開けば同じ場所に着く（Cookie は下記 D のとおりアプリ共有）。
C と組み合わせて初めて境界になる。

## C. ドメイン到達性

Claude がどのサイトへ行けるか。

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **C1. 制限なし** | 実装ゼロ | ユーザーのログイン状態を継承したまま任意のサイトへ行ける。論外 |
| **C2. 静的な許可リスト（設定画面）** | 明快 | 設定 UI が要る。範囲が見えない場所にある。育ちすぎる |
| **C3. タブ由来 + 逐次確認**<br>「制御 on のタブが開いているドメインのみ。新ドメインは確認してから読み込む」 | 許可範囲がタブ列として見える。別 UI が不要。ユーザーが既にやった操作から許可が導かれる | 実装の漏れが 1 箇所でもあると無効。確認疲れ。PiP との衝突（下記） |

C3 の実装時に必ず踏む点:

- **ドメインの定義**は registrable domain（eTLD+1）が妥当だが、**Public Suffix List が要る**。
  「ドットで後ろ 2 つ」だと `co.jp` で破綻し、`foo.co.jp` と `bar.co.jp` が同一扱いになる
- **強制する場所を漏らさない**: `browser_navigate` / `shouldOverrideUrlLoading` /
  `onCreateWindow` / リダイレクト後の確定 URL。メインフレームのみに適用する
  （サブリソースに適用すると CDN で全部壊れる。クロスオリジン iframe は同一オリジンポリシーが
  守るので読めない）
- **リダイレクトは途中で止めない。** OAuth は複数ドメインを跨ぐ連鎖なので、1 ホップごとに
  確認が出ると最悪の場面で確認の嵐になる。**確定 URL で判定**し、拒否なら `goBack()`
- **eval があるうちは `fetch()` がこの網の外。** ナビゲーションではないのでどのフックも見ない。
  クロスオリジンの読み取りは CORS が止めるが、URL にデータを載せた送信は止まらない
- **確認ダイアログは既定を拒否側にし、由来（どのページのどのリンクか）を併記する。**
  ドメイン名だけではユーザーに判断材料がない。複数まとめて出す
- **PiP 中は操作できない**ので、確認には全画面復帰が要る。→ 下記 I のとおり、ツールは
  ブロックせず `pending_user_approval` を即返すこと

## D. Cookie とストレージの分離

**`CookieManager` はアプリ全体で 1 つ。** WebView ごとでもタブごとでもない。つまり
ユーザーが手でログインしたセッションを、Claude はそのまま使える。localStorage と
IndexedDB も同様。**これは v1 の単一 WebView でも起きる。** タブがこの問題を作ったのではなく、
見えるようにしただけ。

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **D1. 共有のまま** | 実装ゼロ。「手動でログインしてから渡す」がそのまま動く | 到達性の制御（C）にバグがあれば、すべてのログイン状態が届く。境界がコードの正しさだけに依存する |
| **D2. 全面分離（Claude 専用プロファイル、ログインなし）** | 硬い境界 | **目的が達成できない。** Claude のタブはどこにもログインしていない |
| **D3. 2 プロファイル**<br>personal（ユーザー）/ agent（Claude） | 境界が**データの物理的な分離**になる。C の実装にバグがあっても personal 側には届かない。「必要なサイトに agent プロファイル内で手動ログインしてから渡す」という運用がそのまま境界になる | 両方で使うサイトには 2 回ログインが要る。**`androidx.webkit` の Multi-Profile API が必要**で、端末の WebView バージョンに依存する（`WebViewFeature.isFeatureSupported()` で要確認） |

D3 が使えるかどうかで、C の重みが変わる。使えなければ C が全荷重を 1 人で負う。

**いずれにせよ、許可した範囲の中では session は生きている。** Amazon を渡せば Claude は
注文できる。範囲を限るのが C と D、範囲内の程度を抑えるのが `browser_request_user`・操作ログ・
即時停止・PiP の可視性。

## E. ページ遷移で状態が失われる問題

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **E1. `fetch()` で読む**（遷移しない） | 実装ゼロ（eval があれば Claude が自分で書く）。元ページが完全に無傷。往復 1 回で速い | JS で描画される詳細ページは生 HTML に中身が無い。**読み取り専用に限ること**（CSRF・副作用） |
| **E2. `goBack()` + BFCache** | 実装ゼロ。効けば **JS の状態ごと**戻る | Android WebView で BFCache が有効かは WebView バージョン依存。**実測が要る**（`window.__mark` を仕込んで往復するだけ） |
| **E3. 自動スナップショット + 検証付き復元** | ツールを増やさずに済む（ナビゲーション直前に自動で積む） | 保存できるのは URL・スクロール位置・フォーム値・`<details>` の開閉まで。**SPA の in-memory 状態は原理的に戻せない**。復元後は「それらしく見えるが中身が違う」状態になりうるので、フィンガープリント照合で検証し、食い違いを正直に返すこと |
| **E4. 本物のタブ（A3）** | 元ページに一切触らない。真に状態を持つ opener ページに対する唯一の解 | A3 のコスト |

E1 と E2 は実装ゼロで、合わせて 30 分ほどで結論が出る。**そこで残った問題の形を見てから
E3 を設計する**のが順当。E3 は緩和策であって解決ではない。

なお E3 のスナップショットは `browser_capture` のサイドカー（スクロール位置を含む）と
ほぼ同じデータを扱うので、コードを共用できる。

## F. autofill

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **F1. 常時 on（現状）** | 現状のまま | Claude のナビゲーションのたびに「パスワードを保存しますか？」が上がりうる。PiP 中にモーダルが出ると詰まる。Claude が JS で埋めた内容が資格情報として保存されうる |
| **F2. 制御中は off** | 手動ログイン → 制御を渡す、という使い方では失うものがない。パスワード値が `browser_read` に載る事故への二重防御になる | フラグ管理 |

F2 の実装: `importantForAutofill` を `NO_EXCLUDE_DESCENDANTS` に切り替える（`NO` だけでは
子孫が残る）。`AutofillManager.cancel()` を併せて呼ぶ。**`onPageStarted` の
`AutofillManager.commit()` も同じフラグでゲートする** — こちらのほうが実害が大きい。

フラグは「Claude を許可」状態に紐づける。`browser_request_user` で全画面に戻すときは
autofill を戻す必要がある。「PiP かどうか」で判定すると全画面でも autofill が死んだままになる。

## G. 永続化とドメイン別削除

| 対象 | 可否 |
| --- | --- |
| パスワード | **既にサポート済み**（system autofill 委譲、永続）。ただし委譲の裏返しで、**ドメインごとの削除 UI は作れない**。プロバイダの設定画面への deep link までが限界 |
| Cookie の永続 | **可能。ただし現状バグの可能性あり** — 書き出しは非同期で、プロセスが死ぬと失われる。`CookieManager.getInstance().flush()` を `onPause` で呼ぶ必要があるが、`BrowserActivity` は呼んでいない |
| localStorage の永続 | **可能**。`domStorageEnabled = true` は既に入っており追加不要 |
| ドメイン別の Cookie 削除 | **可能。ただし列挙 API がない** — 訪問ドメインのリストを自前で持てば、`getCookie()` → 期限切れで `setCookie()` |
| ドメイン別の DOM ストレージ削除 | **おそらく可能、要検証** — `WebStorage.getOrigins()` / `deleteOrigin()` は存在するが古い API で、現行 WebView でのカバー範囲は実測が要る |
| HTTP キャッシュ / Service Worker | **ドメイン単位の API はない。** 全消しのみ |

## H. ツール構成

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **H1. 設計どおり 7 ツール**<br>status / read / click / type / navigate / scroll / request_user | 1 操作あたりのトークンが安い。失敗の仕方が限定される | **どのツールが要るかを実測前に決め打ちすることになる**。アプリ側の実装量が最初から大きい |
| **H2. eval + read の 2 本から** | Android 側が**1 つのプリミティブに収束する**（`evaluateJavascript` して文字列を返すだけ）。**一番危ない仮定を、ツール設計にコミットせずに検証できる**。「同じ JS を毎回書いている」パターンがそのままツールの仕様になる — 会話ログが仕様書になる | Claude が毎回 JS を書くぶんトークンが高く失敗も多い。**eval があるうちはドメイン制限が実効的でない**（パスワード値も読める） |

H2 を採るなら:

- **`(async () => { ... })()` で包む。** そうしないと `await` を含む JS が `null` を返し、
  原因が分からない
- **例外を潰さない。** `{"error": ..., "stack": ...}` を返す。eval ツールの価値の半分はエラーの質
- **戻り値に上限。** WebView 版によって数百 KB で落ちる。切られたことが分からないのが最悪
- **待ちを引数に畳む。** `browser_eval(js, settle=true)`
- **タイムアウトは JS 側を短く**（PHP 側の上限が天井なので、その手前で打ち切る）
- **console 出力を返す**
- **eval は「あとで消す」ではなく別トグルにする。** 後から外す設計は外されない
- `text` 付き DOM 取得は別ツールとして残す。`document.body.innerText` を eval で返すと
  上限なしに膨らむ。切り詰めと要素上限を持った専用ツールが要る

## I. バックグラウンド維持

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **I1. 前面のみ（最小）** | 検証項目が 1 つ減る。端から端まで動かすのが最短 | 画面を離れると止まる |
| **I2. PiP** | `onStop()` が呼ばれずレイアウトが継続する。Claude が何をしているか小窓で見える（**帯域外の検知チャネル**になる） | `configChanges` が必須で、現状のテーマ実装（`recreate()`）と衝突する。PiP のビューポートが小さいので `setScaleX/Y` で縮小する必要がある。**PiP 中は操作できない**ので `request_user` の導線が要る |
| **I3. PiP + Foreground Service** | 画面消灯・放置に耐える | 型の選択（`specialUse`）と OEM 独自キラーへの対処 |

**最初に確かめるべきは「PiP 中に `getBoundingClientRect()` が正しい値を返すか」。**
ここが期待通りなら構想全体が成立する。数十行で確認でき、`DebugLog` がそのまま使える。

同じ検証が**タブにも要る**: `GONE` にした WebView はレイアウトパスが走らず、要素が 1 つも
見つからない。読むタブだけを一時的に `INVISIBLE` にしてレイアウトを 1 回走らせる、という
形にすれば、タブ数に対するメモリコストは線形にならない（Claude は一度に 1 タブしか読まない）。

## J. キャプチャと記録

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **J1. `browser_screenshot` 1 本** | ツールが 1 つ | 記録のたびに画像がコンテキストに積まれ、**会話が数回で破綻する** |
| **J2. `capture` と `screenshot` を分ける** | `capture` は保存してファイル名と URL だけ返す（トークンほぼゼロ）。`screenshot` は DOM から読めないページを**読ませる**ためのもの | ツールが 1 つ増える |

J2 を前提に、記録側で決めておくこと:

- **サイドカーに出自を残す。** `"noteAuthor": "claude" | "user"`、`"capturedBy": "mcp" | "ui"`。
  Claude の入力にはページ本文が含まれるので、インジェクションで攻撃者が選んだ文章が
  git に永久記録されうる。git は忘れないので、後から誰が書いたか判定できない。
  **これが無いとアーカイブ全体の信頼性が下がる**
- **`draw()` はタイルラスタライザを経由しない**ので、画面に白い矩形が出ていてもキャプチャは
  綺麗、という食い違いが起こりうる（[KNOWN-ISSUES.md](KNOWN-ISSUES.md)）。WYSIWYG ではない
- **フルページキャプチャにサイズ上限。** 長いページで数万ピクセル高のビットマップは OOM
- **ファイル名が秒精度**なので連続キャプチャで衝突する
- **保存先（SAF）が未設定のまま制御を渡せないようにする。** `browser_status` に含める

## K. MCP サーバーの認証

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **K1. minimal-mcp のトークン認証を使う** | 「呼べる = 正規ユーザー」が VPS 側で担保される。**`session_key` をツール引数から外せる** — チャットログに credential が残らず、悪意あるコネクタによる中継攻撃も成立しない（B は A のトークンを持たない） | コネクタ登録の手順（`mcp-hash` を消して登録し直す）が要る |
| **K2. 認証なし + `session_key` をツール引数に** | 登録が簡単。ステートレスで実装が単純 | **`session_key` が唯一の credential** になり、毎回のツール呼び出しでチャットログに載る。ログが漏れれば行使される。悪意あるコネクタによる中継が技術的に検出できない。エンドポイントが公開されるので `tools/list` は誰でも引ける |

K2 を採るなら緩和策: 128 bit のランダム文字列、短い TTL（アプリが前面でない状態が数分続いたら
失効）、同時接続 1 に固定、`/pair` のレート制限、device_id の一致確認、操作ログと即時停止。
**残存リスクとして明記する**こと。

## 最小構成

端から端まで動かすことを優先し、危ない仮定を 1 つずつ潰す。上の表からの選択:

| 軸 | 選択 | 理由 |
| --- | --- | --- |
| A. 新規タブ | **A1（何もしない）** | ただし「遷移しなかった」ことを応答に明示し、DOM 抽出に `href` を含める。この 2 つだけで Claude は自力で `navigate` に切り替える |
| B. 可視性 | **B1（1 枚）** | ただしワイヤフォーマットは最初からタブ対応にする（`"tab": 1` と `"tabs": [...]` を常に含め、`tab` を optional 引数として定義）。タブ実装が入った日にツール定義が変わらない |
| C. 到達性 | **C3 の簡易版** | 現在のタブのドメインのみ。新ドメインは全画面で確認 |
| D. Cookie | **D1（共有）** | D3 は Multi-Profile の可否を実測してから |
| E. 状態保持 | **E1 + E2** | 実装ゼロ。E2 は実測項目 |
| F. autofill | **F2（制御中 off）** | 数行で、失うものがない |
| G. 永続化 | `CookieManager.flush()` の追加のみ | 削除 UI は後回し |
| H. ツール | **H2（eval + read）** | 加えて `status`（実装 5 行、無いと未接続時に何も分からない） |
| I. 背景維持 | **I1（前面のみ）** | PiP は端から端まで動いた後に足す。最大の不確定要素を最初の一歩から外す |
| J. キャプチャ | 後回し | ブラウザ操作が動いてから |
| K. 認証 | 未決 | 下記 |

**ブラウザ操作部分はインターフェースで切る。** ツールの実装が `binding.webView` を直接
触らないようにし、`evaluateJs` / `url` / `navigate` / `capture` を持つ層を 1 枚挟む。
v1 ではその実装が 1 つしかない、という形にしておけば、タブ化は「実装が複数になる」だけになる。
これは GeckoView への差し替え、外部ディスプレイへの出力先差し替えと**同じ継ぎ目**。

---

## 実測すべきこと

コードを書く前、あるいは eval が動いた直後に確かめる。どれも短時間で結論が出る。

1. **PiP 中に `getBoundingClientRect()` が正しい値を返すか**（構想全体の前提）
2. **`GONE` → `INVISIBLE` 直後の WebView で同じことが成り立つか**（タブ実装の前提）
3. **BFCache が効くか** — `window.__mark = Date.now()` を仕込んで遷移し、戻って生きているか
4. **`setJavaScriptCanOpenWindowsAutomatically(true)` で、Claude の `element.click()` から
   `onCreateWindow` が発火するか**
5. **Multi-Profile API が使えるか**（`WebViewFeature.isFeatureSupported()`）
6. **`window.opener` が制御境界を跨げてしまうか**
7. **`WebStorage.deleteOrigin()` が localStorage / IndexedDB に実際に効くか**
8. ポーリング往復の実測レイテンシ
